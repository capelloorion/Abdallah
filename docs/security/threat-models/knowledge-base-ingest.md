## 1. Feature summary

Ingestion turns a corpus of `.md`/`.txt` files (planned: the repo's `docs/`, ADR-0013) into chunks,
embeds them with the Foundry embedding deployment and writes them to the Azure AI Search index that
answers every user's questions. Today it is a CLI (`python -m app.ai.ingest <path>`, run by a
developer with a dev key or their identity); ADR-0015 proposes `POST /v1/admin/ingest` (no body,
`202`, background, `409` while running), and ADR-0013 proposes baking `docs/` into the api image at
`/app/corpus`. There is **no authentication**, the api runs 1-6 replicas, and whoever edits the
corpus influences every answer and every citation shown to every user.

**Verdict: acceptable to build `api:4.2` only if** (a) the endpoint is **not** mirrored by the BFF
(recommended answer to Q1, section 5), (b) the corpus is an **explicit allow-list with a secret
scan**, not "everything under `docs/`" (E5/I1), (c) the loader and run budget mitigations K2 and K3
are in its acceptance criteria, and (d) the team accepts the residual risks in section 10. Shipping
the endpoint as ADR-0015 is written today (reachable by any caller that can reach the api, no run
budget, no cooldown, whole `docs/`) is **not recommended**: the unauthenticated cost trigger (D1)
and the whole-`docs/` exposure (I1) are High with no existing pattern that closes them. Nothing here
blocks the CLI path that already exists, but that path has the same corpus risks (I1, T2).

                                                      |

                                                      |--(4)--> Foundry embeddings (batches of 64)

### 5.1 Recommended answer to Q1 ("does the BFF mirror `POST /v1/admin/ingest`?")

**No. The BFF does not mirror it; there is no `apps/web` route, page or button for ingestion.**

Reasons, each tied to the code and rules read for this model:

1. The BFF is the **only browser-facing hop** and today every browser user is anonymous (rule 50).
   Mirroring turns "any user can press re-index" into the design (E2).
2. The BFF has no rate limit and no body limit (shared-conversations R2), so the mirror would also
   be a **public-to-the-network cost amplifier** with no brake.
3. The feature needs no user interaction: ingestion is triggered by an operator or a pipeline after
   a corpus change, never by an end user.
4. It is reversible: a BFF route can be added later behind Okta with its own ADR and a role
   (shared-conversations section 8), whereas an exposed route cannot be un-exposed for the period
   it was open.

What "not mirrored" must mean in practice (all proposed, none on the roadmap):

- A web test asserting that no file exists under `apps/web/src/app/api/v1/admin/` and that the BFF
  route list contains no ingest path (K4). Rule 05 mirrors the upstream version by folder, so the
  absence of the folder is checkable.
- The api route is documented in OpenAPI, so the generated web types will contain it. That is
  fine, but the BFF must not call it; keep it out of the `MOCK_UPSTREAM` fixtures too.
- `docs/architecture.md` (B3, B4a) says the BFF mirrors every route. The team should amend those
  sections (propose a diff; Part B is theirs, ADR-0006). ADR-0015 already recommends this; the
  decision should be recorded there when it moves to Accepted.
- **Who calls it, then?** The api ingress is internal, so the callers are: a developer (CLI, or an
  exec into a replica), a pipeline job in the environment, or another app in the Container Apps
  Environment. That reachability is exactly why the endpoint still needs K3/K4 even without the
  BFF (S1). If nobody has a defined caller, prefer the ADR-0015 alternative (CLI or Container Apps
  Job) in prod and keep the endpoint for dev only (K4). This is open question Q-K1.

## 6. STRIDE

Rating key: **L** = likelihood, **I** = impact (High / Medium / Low). "Residual" is what remains
after the listed mitigation. Status tags: **DONE** (exists in code today) · **PLANNED `<id>`**
(already in a roadmap item) · **PROPOSED `K<n>`** (not on any roadmap item, section 11) ·
**ACCEPTED** (we live with it; `R<n>` refers to section 10).

## 9. What changes when Okta (auth) lands

Auth needs its own ADR and threat model before code (rule 50). This feature must hand over:

1. The route gets an **admin role** check in the api (JWT validation) and is **never** served to
   non-admin users by the BFF; if an admin UI is wanted, it is a new BFF route behind the role with
   its own review. Re-answer Q1 then.
2. The audit event (K12) gains the caller identity (`enduser.id` on the request span only, rule 60;
   still not in metrics or in the document content).
3. The cooldown/budget (K3) stays; per-identity limits are an addition, not a replacement.
4. The shared-visibility consequence of the corpus (I1) does **not** disappear: per-document access
   control in the index (security trimming) is a separate design, needed before any restricted
   document may be ingested.
5. K9 (static token), if adopted, is retired.

## 14. Review triggers (re-run this threat model when any of these happen)

1. **Auth lands** (Okta): section 9; re-rate S1, Rp1, E1, E2.
2. **The ingest route is mirrored in the BFF**, or any admin page is added (reverses Q1).
3. **The api becomes reachable outside the environment**, or the Container Apps Environment's network posture changes.
4. **The corpus scope changes** (new directories, README, `.claude/rules/`, uploaded files, URLs, Blob Storage, a CI-ingest identity) or a document source other than the repo appears.
5. **A tool is added to the graph**, especially one that writes or reads other data (A3).
6. **The index definition, the embedding model or its dimensions change** (D4, K7).
7. **The replica count or hosting model changes** (Container Apps Job, scale rules), or 5.1's mechanism is chosen.
8. **Telemetry changes** that could carry content, or error-handling for the background task changes.
9. **The Search roles or the identity model change** (K8 decision, a new pipeline identity).
10. **An incident**: a secret or sensitive document found in the index, or an unexpected embedding-cost spike.

## 15. Assumptions I could not verify

- The Container Apps Environment's network exposure and which other apps can reach the internal api ingress (platform-owned).
- That `docs/` contains no secrets or confidential material today: **its content was not audited** for this review; only the file list was read.
- Repo governance (CODEOWNERS, required reviews, branch protection, who can merge or open PRs); none was found or inspected.
- Search service behaviour: whether data-plane roles can be scoped to one index, whether vector dimensions can change in place, and whether index aliases are supported by the pinned SDK. These need `docs-lookup` before K7/K8 are designed.
- That ingestion uses `get_embeddings()` (timeouts and retries, `app/ai/client.py`); `run` calls it, but `app/ai/client.py` was not read in this review.
- Foundry/Search retention of embedding inputs and queries.
- That the SQLAlchemy/FastAPI instrumentors do not record request bodies; not relevant to this route's body (none) but relevant to the failure path.
- Container Apps scale-in behaviour for in-flight background tasks (Q-K6).
- No endpoint, lease table or `corpus` directory exists yet; every mitigation tagged PLANNED or PROPOSED is a requirement, not a statement about existing code. The statements tagged DONE refer to `ingest.py`, `retrieve.py`, `graph.py`, `prompts/system.md` and `.dockerignore` as read on 2026-10-06.
