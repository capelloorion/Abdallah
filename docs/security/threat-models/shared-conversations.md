## 1. Feature summary

Team Assistant keeps chat history in Azure SQL (`conversations`, `messages`). There is no login and
no owner column (ADR-0014), so **every user can list, open and continue every conversation**, and
what they type is kept **indefinitely** with no delete, rename or purge path. The api surface
`POST/GET /v1/conversations` and `GET /v1/conversations/{id}` is implemented (api:1.2); the code
that writes questions and answers (ask endpoints), the web chat UI and BFF routes, and the search
index are **planned, not built**.

**Verdict: acceptable to proceed only for an internal, trusted-network deployment, and only if the
team accepts the residual risks in section 9.** Nothing here blocks api:1.2 (it writes no message
content). `api:2.2` must not start until the team accepts this document and the mitigations tagged
`2.2` are in its acceptance criteria. If the app is ever reachable outside the internal network, or
real user identities appear, this design must not ship as is (section 13).

## 3. Assets and data classification

Everything below is **user-generated free text**; the team cannot constrain what people paste.
Classification is therefore "Internal, may contain Confidential or personal data by accident".

| Asset                                      | Where                                                     | Class                                   | Who can read today                                                                               |
| ------------------------------------------ | --------------------------------------------------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Conversation title (first question, <=200) | `conversations.title`, **shown in the list**              | Internal, possibly personal             | Every user, from the list (no need to open the chat)                                             |
| Questions                                  | `messages.content` (role `user`)                          | Internal, possibly personal or secret   | Every user                                                                                       |
| Assistant answers                          | `messages.content` (role `assistant`)                     | Internal (derived from the docs corpus) | Every user                                                                                       |
| Citations `{title, path}`                  | `messages.citations` (JSON text)                          | Internal                                | Every user                                                                                       |
| History sent to the model                  | Request to the Foundry chat deployment (last 10 messages) | Internal, possibly personal             | Foundry platform (cloud-team owned); its retention is **an assumption to verify** (Q5)           |
| Retrieval queries                          | Request to Azure AI Search (the last question)            | Internal, possibly personal             | Search platform (cloud-team owned)                                                               |
| Telemetry (logs, spans, metrics, events)   | Log Analytics / App Insights                              | Must contain **no content**             | Anyone with workspace access                                                                     |
| Backups / point-in-time restore            | Azure SQL                                                 | Same as the data                        | Azure SQL admins; retention is the platform default (**assumption**: not configured in `infra/`) |

## 4. Trust boundaries and data flows

```text
 Browser --(1)--> apps/web BFF --(2)--> apps/api --(3)--> Azure SQL (conversations, messages)
                                           |
                                           |--(4)--> Azure AI Search      (planned: last question)
                                           '--(5)--> Foundry chat model   (planned: <=10 messages of history + context)
 apps/web, apps/api --(6)--> Azure Monitor (telemetry; must carry no content)
```

| #    | Boundary / flow           | Today                                                                                                                                                                                                                                                                                                                                                                  |
| ---- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | Browser -> BFF            | **No authentication.** The only control is network placement ("internal only", team decision D8). A client-supplied `x-trace-id` is correlation, never trust.                                                                                                                                                                                                          |
| 2    | BFF -> api                | The api trusts whoever reaches it; the BFF is the only intended caller (rule 50). `infra/main.bicep` sets the api ingress internal (`externalIngress: false`) and the web ingress **external** (`externalIngress: true`); whether the Container Apps Environment itself is on a private network is platform-tier and **not verified here (assumption)**.               |
| 3    | api -> Azure SQL          | ORM-parameterised queries; managed identity when deployed. `infra/modules/sql-database.bicep` declares a **public endpoint** with the `AllowAllWindowsAzureIps` rule (any Azure service) plus developer IPs, Entra-only auth. That file is marked "assumed interface, placeholder until the infra team's file arrives (D9)", so the network posture is **unverified**. |
| 4, 5 | api -> Search / Foundry   | Managed identity; planned. Both are shared platform services owned by the cloud team.                                                                                                                                                                                                                                                                                  |
| 6    | Services -> Azure Monitor | Redaction covers secret-named fields only, **not content** (rule 60), so content must never be logged at all.                                                                                                                                                                                                                                                          |

**The one control that decides everything is "who can reach the BFF".** There is no second line of
defence for reads or writes.

## 6. STRIDE

Rating key: **L** = likelihood, **I** = impact (High / Medium / Low). "Residual" is what remains
after the listed mitigation. Status tags: **DONE** (api:1.2) · **PLANNED `<id>`** (already in a
roadmap item) · **PROPOSED `P<n>`** (not in any roadmap item yet, see section 10) · **ACCEPTED**
(we live with it; the `R<n>` refers to section 9).

| T2  | **Conversation poisoning of the model's context.** The "last 10 messages" are replayed to the model, so an attacker's messages in a shared thread become model input for every later user of that thread (see A1).                                                | Medium / Medium | AI section A1 (history as data, user/assistant roles only, output constraints, eval cases). **PLANNED 2.2/3.1.**                                                                                                                                                                                                                                                                                                                                             | **Medium, ACCEPTED (R1)**, reduced by A1.                                                                                                                          |

### 6.5 Denial of service

### 6.6 Elevation of privilege

There are no roles to elevate. The risks are exposing a capability that should not be exposed, and
the later move to auth.

| ID  | Threat                                                                                                                                                                                                                  | L / I         | Mitigation (where, status)                                                                                                                                                                                                                                        | Residual                                                                                            |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| E1  | **IDOR is the design**: `GET /v1/conversations/{id}` and the planned `/ask` do no ownership check (`repositories/conversations.py` filters by id only). "Privacy by uuid" is not an argument: the list returns all ids. | High / Medium | Accepted shared model (R1). Code docstrings already state that no query filters by owner. Do not add owner-like hints such as a cookie id (rejected in ADR-0014).                                                                                                 | **ACCEPTED (R1)**; ends when auth lands.                                                            |
| E2  | **A BFF route exposes a backend capability it should not**: mirroring `POST /v1/admin/ingest` (api Q1) would let any browser user trigger a cost-bearing job; a catch-all proxy would expose every api route.           | Medium / High | Mirror only what the UI needs: conversations list/create/get and ask-stream. Ingest is **not** mirrored unless Q1 says so (api 4.2; own model in `knowledge-base-ingest.md`). Explicit BFF route files, no pass-through proxy (rule 50). **PLANNED web 1.1/1.2.** | **Low**: control is explicit routes plus review of the BFF route list; recheck when Q1 is decided.  |
| E3  | **An admin-only action done by anyone**: with no roles, any user could call a future delete/purge endpoint.                                                                                                             | Medium / High | **Do not add a delete or purge HTTP route without auth.** Purge is an operator action in SQL (P3), not an endpoint. Adding any delete/rename endpoint is a review trigger (section 13).                                                                           | **Low** while no such route exists (control: it does not exist; ADR-0014 puts delete out of scope). |

## 8. What changes when Okta (auth) lands

Auth needs its own ADR and threat model before code (rule 50). This section lists only what **this**
feature must hand over.

1. **Add an owner column** by a new migration (ADR-0014). Every repository query (list, get, ask,
   any purge) must filter by owner; the current "no query filters by an owner" docstrings are the
   checklist of places to change.
2. **Backfill of ownerless rows is the hard part.** Options: (a) assign them to a placeholder
   "legacy/shared" owner and keep them visible to all (keeps the exposure, so decide whether that is
   acceptable for content that may already hold personal data); (b) delete them; (c) have an admin
   triage. Because the FK is `NO ACTION`, deleting needs `messages` first. It is a data migration on a
   populated table with `nvarchar(max)` columns: plan batches and a backup first. The auth ADR decides.
3. **Authorization (IDOR):** another owner's conversation id returns `404`, not `403` (no existence
   leak); the list filters by owner; ask checks ownership **before** the user message is stored.
4. **Telemetry:** rule 60 allows `enduser.id` on request spans only after auth; conversation and
   message content stays out regardless.
5. **Repudiation** closes partly; add a `created_by` on messages if any thread stays shared.
6. **Delete / rename / purge** can then be offered per owner; re-run this model.
7. **Past exposure stays:** pre-auth rows were written with a "visible to all" expectation; making
   them private later does not undo who already saw them.

## 13. Review triggers (re-run this threat model when any of these happen)

1. **Auth lands** (Okta or any identity): needs its own ADR and threat model; do the section 8 work and re-rate the Spoofing, Repudiation, I1 and E1 rows.
2. **A delete, rename or purge path is added** (endpoint or scheduled job), or a retention period is decided.
3. **The app is deployed or reachable outside the internal network** (public ingress, partner access, guest users, a new network path).
4. **The corpus or tools change**: new document sources, an external-database tool, `AI_ALLOW_TEXT_TO_SQL`, any tool that mutates data, or any tool that reads `conversations`/`messages`.
5. **Message-writing code lands** (api 2.2/3.1) and when the web chat ships: re-run against the real code.
6. **Content handling changes**: Markdown or HTML rendering of answers, attachments or file upload, sharing or export, search over history, a change to the history length sent to the model.
7. **The model or search platform changes** (a different deployment, a third-party model, a retention setting change).
8. **Telemetry changes** that could carry content (new span attributes, custom events, log fields).
9. **The SQL module is replaced** by the infra team's file, or the database's network posture changes.
10. **An incident**: any report of personal data or a secret in chat or in logs.

## 14. Assumptions I could not verify

- The network is internal-only; the Container Apps Environment's exposure is platform-owned and not in this repo (the web ingress is declared external in `infra/main.bicep`).
- The infra SQL module is a placeholder awaiting the infra team's version; its firewall and backup settings may change.
- Foundry and Search data retention and abuse-monitoring behaviour.
- That the SQLAlchemy and FastAPI OpenTelemetry instrumentors do not record bound parameters or request bodies by default (their configuration was not inspected); the engines do not set `hide_parameters`.
- That no BFF rate limit or body limit exists (no BFF conversation code was read; the web roadmap has none).
- Migration `0001` has not been applied; the real-database checks in the api:1.2 `needs_human` list are still open.
- No code under `apps/web` or `app/ai/` was read for this review; the AI and web mitigations are requirements for planned work, not statements about existing code.
